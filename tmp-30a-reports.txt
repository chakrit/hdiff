## Violations

### V1 — a hunk range's start and a binary block's size are parsed into numbers only to be dropped

`src/parser/hunk.rs:178-186` (`range_count`) and `src/parser/binary_patch.rs:76-77`
(`check_binary_block_size`). `decimal_count(start)?;` parses the start into a `usize`
and discards it, `decimal_count(range).map(|_| 1)` does the same for a countless range,
and `binary_block_field(header).and_then(decimal_count).is_some()` parses the block size
only to ask whether it parsed. Round 14 V11 ruled exactly this shape a Violation ("some
values are parsed only to check them and then dropped: the binary block size in
`parse_binary_patch` and `start` in `range_count`"); round 15 fixed it with
`is_decimal_count`, and round 19's `decimal_count` merge brought the parse-and-drop back.
A side effect is an unstated rule: a start or size beyond `usize::MAX` is rejected as
malformed, which the input contract's "in ASCII digits" does not say.

Fix: give the parser one `is_decimal(field)` check (ASCII digits, nonempty) beside
`decimal_count`, used where only well-formedness matters, so a dropped value cannot be
written.

### V2 — `Family::stages` is non-empty only by `chunk_by`'s guarantee, and its parent is read by index

`src/measurement.rs:21-28,55-58`. `Stage::families` builds each `Family` from a
`chunk_by` slice and reads `stages[0].parent()`. The slice is never empty, but nothing in
`Family`'s type says so, and the index is the read-by-position shape earlier rounds ruled
out (round 13, round 16 V7); `NonEmpty` exists for at-least-one sequences (round 12 V1).

Fix: destructure the chunk (`let [first, ..] = stages`, or `split_first`) where the
family is built, so the parent comes from a named first stage, or hold the family's
stages in a type that cannot be empty.

### V3 — `std::os::unix::fs::symlink` is written out in full twice

`src/actions/install_git_diff_pager.rs:362,388` (tests). `rust-coding` imports a path
used more than once, and a four-segment path is imported even when used once. The test
module already imports `fs`.

Fix: `use std::os::unix::fs::symlink;` in the test module and call `symlink(..)`.

## Violations

### V1. `RowTone::of` binds a `RecordKind` under its `LineKind` parameter's name

`src/styling.rs:116-124`: `fn of(kind: LineKind)` matches `kind` and, in the payload arm,
binds the record's `RecordKind` as `kind`, then calls `kind.changed_side()` — one name
for two values of two types in one expression, which rounds 11, 12 and 28 ruled a
Violation (`code`, One Reading). Fix: bind the field as `record_kind: kind`, or name the
parameter `line_kind`.

### V2. A pair is walked with its sides by pairing it with a separate `Side::BOTH` list

`src/detail.rs:246` writes `Side::BOTH.into_iter().zip(*runs)`, and the theme test
`draws_unchanged_detail_text_dimmer_than_line_mode_text` (`src/theme.rs:424-425`) loops
`for side in Side::BOTH` and reads `change.get(side)`, the shape round 13 and round 28
V4 ruled out. The zip is correct only because `Side::BOTH` and `BySide`'s `IntoIterator`
both happen to list old first; nothing ties the two orders together (`architect`,
Correct by Construction). Fix: one `BySide` method that yields each value with its side
(for example `into_sides() -> [(Side, T); 2]` or an iterator built from `map_sides`),
used by both sites.

### V3. `ColorDepth::of_color_count` decides its third case with a wildcard arm

`src/theme.rs:22-26` matches the count against `u16::MAX`, `256..` and `_ => Basic`. The
last arm names no case; `..=255` does, and the match stays exhaustive. Rounds 13, 14 and
26 ruled wildcard arms that stand for a nameable case a Violation (`code`, One
Reading). Fix: `..=255 => Self::Basic`.

## Violations

### V1 — a side is paired with its value by hand in three places

`BySide` owns the old-then-new order and offers `map`, `map_sides`, `iter`, `zip` and
`merge`, but three sites still walk the sides by pairing a `Side` with its value
themselves:

- `src/detail.rs:246`: `Side::BOTH.into_iter().zip(*runs)` pairs each side with its run
  for `cursor.mark(side, …)`. The pairing relies on `BySide`'s iteration order matching
  `Side::BOTH`, knowledge that belongs to `BySide` alone. Round 29 introduced this form
  for round 28 rendering V4; it breaks the round 13 ruling that sides are walked through
  `BySide`'s own iteration, not rebuilt from `Side::BOTH`.
- `src/theme.rs:424-425`: the palette test loops `for side in Side::BOTH` and reads
  `change.get(side)`, the exact shape round 13 ruled a Violation.
- `src/terminal/view.rs:166`: `BySide::of(|side| panes.get(side).content())` rebuilds a
  `map` through `of` and `get`; it is `panes.as_ref().map(ContinuityFrame::content)`
  (or equivalent) before `merge(Rect::union)`.

Fix: give `BySide` one iteration that yields each side with its value (for example
`sides()` yielding `(Side, &T)`, or `into_sides()` by value), use it at
`detail.rs:246` and `theme.rs:424`, and write `view.rs:166` as a `map` over the pair.
Owners: `side.rs`, `detail.rs`, `theme.rs` (test), `terminal/view.rs`.
